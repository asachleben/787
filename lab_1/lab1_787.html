R Projects

Whenever you are undertaking a new research project, it is good practice to create an RStudio project for that entire research project. Your RStudio project can help streamline your research pipeline, and make your work easily reproducible, from start to finish.

Working within an .Rproj has three main advantages:

  • Self-contained workspace: all scripts, data, and outputs for a specific paper (or dissertation chapter) are saved in a single place.

  • Automatic working directory: opening an R project automatically sets your working directory to the project’s root folder. This helps eliminate the need for the machine-specific setwd() commands.

  • Easier collaboration and replication: the root directory is standardized, so all of your references to other folders or files (such as loading in data) can use relative file paths, which will let your code run more seamlessly on your co-author’s machine, or on a replication server.

Organizing Your Project Directory

While creating an .Rproj file is a helpful first step, I’ve also found that sticking to a consistent subfolder structure within your project is what really helps keep your research pipeline organized.

The exact folder names you choose are ultimately a matter of personal preference, but keeping the same structure across all your research projects will save you countless hours (especially if you’re returning to a paper months later to address reviewer comments!).

I’ve found the following structure to be highly effective. Like I said, what your subfolders in a project look like is up to you, but I think it helps to pick a style and be consistent:

  • Code/: Contains all .R, .Rmd, and .py, scripts. I also like to name these numerically to indicate the order in which they run (e.g., 1. pulling_record, 2. cleaning_files, 3. parsing_speeches)

  • Data/: Houses all data for the project. I also find it helpful to keep your raw data separate from your clean working data within this folder

  • Literature/: self-explanatory

  • Paper/: Contains manuscript drafts (I typically save with the date if I’m making large changes rather than overwriting)

  • Figures/: Contains all of your saved plots, graphs, regression tables, etc. Basically anything you create in R that’s going into your paper is saved here

R Environments

One of the main benefits of projects is when they are used in conjunction with Posit’s virtual environments for R via the renv package. While RStudio projects help organize your files, they do not manage your packages, which is what the renv package can do for you.

Using renv replaces your global R library with a project-specific library. This provides two big advantages for researchers:

  • Version control for packages: Using renv, your project relies only on the exact package versions you installed for that project. Sometimes, you may need to use multiple versions of a package across different projects. It may also be the case that packages from different projects are not compatible with one another (e.g. MASS package masks the ‘select’ command from dplyr).

  • Streamlining collaboration: renci tracks your dependencies in a renv.lock file. By sharing this file (via Github or even Dropbox), your co-authors can automatically download and install the exact R environment you were using.

Exercise: Building renv Pipeline

Let’s implement the renv workflow for this project. This is good practice to implement with your own projects as well. Make sure you are currently inside the POLI787_Lab1 project we just created, and run through the following steps in your console:

  1. Initialize the environment. For each project, you need to turn on renv. This command creates your project library and generates the first renv.lock file.
# install package, if not already present
if(!require("renv")) install.packages("renv")

# initialize renv for current project
renv::init()
  1. Install packages. Because renv has been initialized, these installed packages will be loaded into your project-specific environment, rather than your global R environment There are two options for installing packages:
  • As you normally would, via “install.packages”:
# install the tidyr package
install.packages("tidyr")
  • Through renv’s specific package installation:
# install the dplyr package
renv::install("dplyr@1.1.0") # this can be helpful for installing specific versions of packages

  1. Snapshot the environment. Once you’ve installed packages (and your code is working), you need to save the state of your environment to the renv.lock file. You should do this periodically as you add new packages to your project.
# save the current state of your project's library

If you were to take a turn working in a shared script, you would rely on the renv.lock file to make sure that you and your co-author are working in the exact same R environment. You do this using the “restore” command:
# unstalls the exact package versions recorded in the renv.lock file for the project
renv::restore()
#>>> - The library is already synchronized with the lockfile.

# Update a specific package
renv::update("dplyr")
