Research Pipelines in R

As you begin working on your own projects, it is important to develop a consistent workflow for organizing your data, code, and analysis. Good research pipelines make projects easier to manage, to return to months later, and to reproduce. If you already have ongoing research projects, now is a good time to start thinking critically about your current workflow.

Today’s lab focuses on three parts of building and maintaining a research pipeline in R. First, we’ll discuss project setup and environments, including how to organize projects so that your code is portable and reproducible. Second, we’ll talk about debugging code and work through an example. Finally, we will introduce profiling as a tool for diagnosing inefficient code and identifying where changes can be made to optimize your code.

There are also several broader principles that we will not spend much time reviewing today but that you should always practice through your research:

  • Comment your code clearly! You should be able to understand why you made a particular decision when you return to a script months later.

  • Write clean and readable code. Consistency and clarity in naming, formatting, and organization make both debugging and collaborating much easier.

  • Check your work as you go. Do not wait until the end of a long pipeline to see whether the final result looks plausible. Inspect the intermediate dataframes, variables, and outputs throughout the entire process to make sure your code is doing what you intended.

Broadly, your goal should not just be to have code that runs. Rather, you should try to build a research process/workflow in which you can understand, reproduce, and defend each step (and decision) between the original data and your final results.

R Projects – RStudio Specific

Whenever you are undertaking a new research project, it is good practice to create an RStudio project for that entire research project. Your RStudio project can help streamline your research pipeline, and make your work easily reproducible.

Working within an .Rproj has three main advantages:

  • Self-contained workspace: all scripts, data, and outputs for a specific paper (or dissertation chapter) are saved in a single place.

  • Automatic working directory: opening an R project automatically sets your working directory to the project’s root folder. This helps eliminate the need for the machine-specific setwd() commands.

  • Easier collaboration and replication: the root directory is standardized, so all of your references to other folders or files (such as loading in data) can use relative file paths, which will let your code run more seamlessly on your co-author’s machine or on a replication server.

Organizing Your Project Directory

While creating an .Rproj file is a helpful first step, I’ve also found that sticking to a consistent subfolder structure within your project is what really helps keep your research pipeline organized. The same is true if you’re just working in a Dropbox folder.

The exact folder names you choose are ultimately a matter of personal preference, but keeping the same structure across all your research projects will save you countless hours (especially if you’re returning to a paper months later to address reviewer comments!).

I’ve found the following structure to be highly effective. Like I said, what your subfolders in a project look like is up to you, but I think it helps to pick a style and be consistent:

  • Code/: Contains all .R, .Rmd, and .py, scripts. I also like to name these numerically to indicate the order in which they run (e.g., 1. pulling_record, 2. cleaning_files, 3. parsing_speeches)

  • Data/: Contains all data for the project. I also find it helpful to keep your raw data separate from your clean working data within this folder

  • Literature/: self-explanatory

  • Paper/: Contains manuscript drafts (I typically save with the date if I’m making large changes rather than overwriting)

  • Figures/: Contains all of your saved plots, graphs, regression tables, etc. Basically anything you create in R that’s going into your paper is saved here

Tip: You can generate this structure in your console right after creating your project:

# create standard sub-directories 
purrr::walk(c("Code", "Data", "Literature", "Paper", "Figures"), dir.create)

Environments

One of the main benefits of projects is when they are used in conjunction with Posit’s virtual environments for R via the renv package. While RStudio projects help organize your files, they do not manage your packages, which is what the renv package can do for you.

Using renv replaces your global R library with a project-specific library. This provides two big advantages for researchers:

  • Version control for packages: Using renv, your project relies only on the exact package versions you installed for that project. Sometimes, you may need to use multiple versions of a package across different projects. It may also be the case that packages from different projects are not compatible with one another (e.g. MASS package masks the ‘select’ command from dplyr).

  • Streamlining collaboration: renv tracks your dependencies in a renv.lock file. By sharing this file (via Github or even Dropbox), your co-authors can automatically download and install the exact R environment you were using.

Example: Building renv Pipeline

Let’s implement the renv workflow for this project. This is good practice to implement with your own projects as well. Make sure you are currently inside the POLI787_Lab1 project we just created. If you are working in Positron, make sure you are in a 787 Lab 1 folder. Then, run through the following steps in your console:

  1. Initialize the environment. For each project, you need to turn on renv. This command creates your project library and generates the first renv.lock file.
# install package, if not already present
if(!require("renv")) install.packages("renv")

# initialize renv for current project
renv::init()
  1. Install packages. Because renv has been initialized, these installed packages will be loaded into your project-specific environment, rather than your global R environment There are two options for installing packages:
  • As you normally would, via “install.packages”:
# install the tidyr package
install.packages("tidyr")
  • Through renv’s specific package installation:
# install the dplyr package
renv::install("dplyr@1.1.0") # this can be helpful for installing specific versions of packages
  1. Snapshot the environment. Once you’ve installed packages (and your code is working), you need to save the state of your environment to the renv.lock file. You should do this periodically as you add new packages to your project.
# save the current state of your project's library
renv::snapshot()
  1. Restore the environment. This is what is particularly useful when collaborating. If you were to take a turn working in a shared script, you would rely on the renv.lock file to make sure that you and your co-author are working in the exact same R environment. You do this using the “restore” command:
# installs the exact package versions recorded in the renv.lock file for the project
renv::restore()
  1. Updating Packages If you ever need to update a packagewithin your renv environment, you can use the update function. Once you’ve confirmed that your code still runs with the updated package, you should take another snapshot to record the change to the environment.
# update a specific package
renv::update("dplyr")

# save new version of renv.lock file (after confirming code runs)
renv::snapshot()

Git and GitHub

Git and GitHub are tools for keeping track of changes to your research projects as they develop. Git is a version control system that records changes to files over time, which allows you to see what changed and when, and to return to an earlier version of a file if something goes wrong. GitHub is an online platform that works with Git to store repositories (collections of files) remotely and makes it easier to share projects and collaborate with others.

Version control is a helpful part of your research pipeline because it provides a history of the code you’ve written, the analysis you’ve done, and what changes you and your coauthors have made. Keeping a clear record of these changes makes it much easier to identify when something went wrong, recover earlier versions of your work, and understand how your analysis developed over time. Version control also makes it much easier to collaborate with coauthors without passing different versions of scripts and files back and forth.

Most used Git commands:

  • Clone: Creates a local copy of an existing GitHub repository

  • Pull: Gets the newest changes from GitHub and incorporates them into your local repository

  • Add: Stages your changed files for the next commit

  • Commit: Saves the stages changes as a new version of the project

  • Push: Uploads your local commits (changed files) to GitHub

The basic workflow for GitHub is therefore:

GitHub –> pull –> Local Repository –> add –> Staging Area –> commit –> Local Repository –> push –> GitHub

Debugging Code

Debugging is an evitable part of writing code. As your code becomes more complex, the likelihood that you will encounter errors, unexpected outputs, or code that runs different than you expected increases. Being able to identify the source of these problems and correct them is critical.

Although LLMs can be useful for helping diagnose and fix coding problems, they are definitely not a substitute for understanding how your own code works. In order to be able to effectively work with an LLM to fix your code, you need to be able to inspect the objects at various stages of your code and be able to evaluate whether a proposed solution actually addresses the underlying problem. Developing these skills and knowing your coding principles will also make you better at using tools like LLMs because you will be prepared to evaluate suggestions from an LLM rather than simply implementing suggested changes without understanding them. Also, LLMs can make mistakes! As the author responsible for a research project, you are ultimately responsible for each line of code and everything that you produce. Relying blindly on an LLM is not a good strategy, but understanding your code is.

When debugging your code, a good first step is always to inspect the error, because sometimes it’s super simple. For example, what is the error below?

# try to calculate the mean of several values
meann(c(1, 2, 3, 4, 5))

Other times, however, debugging code can be a much more complicated process, especially if you’re not exactly sure where in your code the error is coming from. In those instances, there are several functions that can help you debug your own code, without just asking an LLM. traceback() displays the sequence of function calls that led up to the most recent error. debug() allows you to walk through a function one statement at a time, so you can inspect your environment after each execution to find the error. debugonce() does the same thing but only for the next call to that function. Finally, browser() allows you to choose a point in your code where the code should pause so that you can inspect the current environment and see if there are errors.

Debugging Code Exercise

Now that you’ve learned about the debugging functions, let’s put them into practice. As a review of material from POLI 784, we will simulate data and fit an OLS regression model, while debugging code along the way.

Rather than simulating all of our variables inside a single function, we will build our data simulation as a series of smaller functions. The argument each function takes is the number of observations you want to simulate.

# set seed for reproducibility
set.seed(9692)


### create function to simulate gender
simulate_gender <- function(N) {
  
  # simulate gender
  X1 <- sample(
    x = c(
      rep(0, N*0.5), # male
      rep(1, N*0.5) # female
    ),
    size = N,
    replace = FALSE
  )
  
  # return simulated gender
  return(X1)
}


### create function to simulate religious affiliation
simulate_religion <- function(N) {
  
  # create probabilities for religious affiliation
  rel_probabilities <- c(
    0.45, # protestant
    0.20, # catholic
    0.15, # jewish
    0.10, # muslim
    0.10 # other
  )
  
  # simulate religious affiliation
  X2 <- sample(
    x = c(1, 2, 3, 4, 5),
    size = N,
    replace = TRUE,
    prob = rel_probability
  )
  
  # convert religious affiliation to factor
  X2 <- factor(
    X2,
    levels = c(1, 2, 3, 4, 5),
    labels = c(
      "Protestant",
      "Catholic",
      "Jewish",
      "Muslim",
      "Other"
    )
  )
  
  # return simulated religious affiliation
  return(X2)
}


### create function to simulate demographic variables
simulate_demographics <- function(N) {
  
  # simulate biological sex
  X1 <- simulate_gender(N)
  
  # simulate religious affiliation
  X2 <- simulate_religion(N)
  
  # combine demographic variables
  demographics <- data.frame(
    X1 = X1,
    X2 = X2
  )
  
  # return simulated demographic variables
  return(demographics)
}


### create function to simulate years of education
simulate_years_education <- function(N) {
  
  # simulate years of education
  X3 <- sample(
    x = c(
      rep(11, N*0.10), # did not complete high school
      rep(12, N*0.35), # high school
      rep(16, N*0.35), # college
      rep(18, N*0.20) # college plus graduate
    ),
    size = N,
    replace = FALSE
  )
  
  # return simulated years of education
  return(X3)
}


### create function to indicate more than high school education
create_education_indicator <- function(X3) {
  
  # create indicator for graduate education
  X4 <- ifelse(
    X3 <= 18,
    0,
    1
  )
  
  # convert more than high school to factor
  X4 <- factor(
    X4,
    levels = c(0, 1),
    labels = c(
      "No Graduate Education",
      "Graduate Education"
    )
  )
  
  # return education indicator
  return(X4)
}



# create function to simulate education variables
simulate_education <- function(N) {
  
  # simulate years of education
  X3 <- simulate_years_education(N)
  
  # create indicator for more than high school
  X4 <- create_education_indicator(X3)
  
  # combine education variables
  education <- data.frame(
    X3 = X3,
    X4 = X4
  )
  
  # return simulated education variables
  return(education)
}


### create function to simulate age
simulate_age <- function(N) {
  
  # initialize age vector
  X5 <- rep(NA, N)
  
  # simulate age one observation at a time
  for (i in 1:N) {
    
    # randomly determine age distribution
    age_distribution <- sample(
      x = c(1, 2),
      size = 1,
      replace = TRUE,
      prob = c(0.75, 0.25)
    )
    
    # simulate younger age distribution
    if (age_distribution == 1) {
      
      X5[i] <- runif(
        n = 1,
        min = 18,
        max = 70
      )
      
    }
    
    # simulate older age distribution
    if (age_distribution == 2) {
      
      age_value <- rnorm(
        n = 1,
        mean = 70,
        sd = 10
      )
      
      if (age_value < 70) {
        
        age_value <- 
          age_value + 
          (2*(70 - age_value))
        
      }
      
      X5[i] <- age_value
      
    }
    
  }
  
  # round age to nearest year
  X5 <- round(X5)
  
  # return simulated age
  return(X5)
}


### create function to simulate outcome variable
simulate_outcome <- function(df) {
  
  # simulate outcome variable
  Y <- round(
    35 + 
    5*df$X1 +
    3*(df$X2 == "Protestant") + 
    5*(df$X2 == "Catholic") + 
    6*(df$X2 == "Jewish") + 
    (-5)*(df$X2 == "Muslim") +
    0.75*(df$X3 - 12) +
    0.25*df$X5 + 
    rnorm(
      n = nrow(df),
      mean = 0,
      sd = 12.5
    )
  )
  
  # return simulated outcome
  return(Y)
}


# create function to simulate full dataset
simulate_data <- function(N) {
  
  # simulate demographic variables
  demographics <- simulate_demographics(N)
  
  # simulate education variables
  education <- simulate_education(N)
  
  # simulate age
  age <- simulate_age(N)
  
  # combine simulated variables
  df <- data.frame(
    X1 = demographics$X1,
    X2 = demographics$X2,
    X3 = education$X3,
    X4 = education$X4,
    X5 = age
  )
  
  # simulate outcome variable
  df$Y <- simulate_outcome(df)
  
  # return simulated data
  return(df)
}

Profiling Code Exercise

Returning to the code you previously debugged, while we now have working code, we don’t necessarily have efficient code. As your research pipelines become larger and more complex, inefficient code can increase the amount of time it takes to complete your analysis, especially if you are working with very large datasets.

Profiling is the process of determining where code is spending its time while running. Rather than just guess which parts of code are inefficient, profiling lets us identify which functions or operations accound for the largest portions of the total runtime. Using these diagnostics, we can then focus on optimizing the parts of our code where improving efficiency will matter most.

Before profiling individual pieces of code, we can first use system.time() to see how long the entire data simulation takes.

# set sample size to 1000000 for profiling
N <- _______

# measure how long it takes to simulate data
_________({
  df <- simulate_data(N)
})

While system.time() tells us how long it takes to complete this simulation generally, it does not tell us which parts of the simulation function take up the most time. To examine our code at a more granular level, we csn use Rprof(). Rprof() records which functions are being executed and where the code is spending the most time running. Rprof() doesn’t replace or change any of the code that’s running, it’s just observing and tracking what R is doing while your code is running. We can then use the summaryRprof() to inspect the results and identify where out code is spending the most time.

# start profiling revised code
________("simulation_profile.out")

# simulate data
df <- simulate_data(N)

# stop profiling code
Rprof(NULL)

# summarize profiling results
profiling_results <- __________(
  "simulation_profile.out"
)

# examine profiling results
profiling_results$by.total
